Runtime Guide

Implemented runtime behavior in the official Polonio Reference Distribution.

Language, Runtimes, and the Reference Distribution

The Polonio Language is syntax, values, semantics, control flow, and Layer 1 Language Core support. The Standard Library supplies general string, collection, math, date, escaping, and URL helpers. Neither definition requires HTTP or SQLite.

The Template Runtime renders templates with interpolation, includes, and ordered output. The Web Runtime supplies request/response execution, sessions, CSRF, uploads, file responses, and file-mode mail. The Data Runtime supplies sandboxed storage and SQLite. The Reference Distribution is the official executable that ships all of these layers.

CGI and polonio serve are Reference Distribution Web Runtime adapters, not language requirements. See the conformance profiles and conformance matrix for exact guarantees.

Template Runtime

Templates combine literal text with <% ... %> code blocks, $variable interpolation, and the echo language statement. Includes are resolved during template rendering. The Template Runtime provides print and println; it does not require HTTP, CGI, storage, or SQLite.

Start with the Language Reference for syntax and the Examples page for executable templates.

Web Runtime

The Web Runtime provides request and response contexts. It populates _GET, _POST, _FILES, _COOKIE, and _SERVER; offers request helpers; and supports response helpers, sessions, CSRF, uploads, send_file, and file-mode send_mail. These APIs require the documented request, response, session-secret, or storage context.

CGI adapter

With no CLI arguments and GATEWAY_INTERFACE set, the Reference Distribution enters CGI mode. It resolves a script from SCRIPT_FILENAME or PATH_TRANSLATED, reads CGI environment variables and CONTENT_LENGTH bytes from stdin, then writes CGI headers followed by the rendered body. CGI errors produce a plain-text 500 response.

Development-server adapter

polonio serve [--root DIR] [--port N]

The defaults are the current directory and port 8080. The server binds only 127.0.0.1, serves static files, renders .pol files, resolves extensionless paths to matching templates, uses index.pol then index.html for directories, and renders root-local 404.pol when present. It supports GET and POST.

Request and response processing

Query strings populate _GET. URL-encoded POST bodies populate _POST; multipart form fields and files populate _POST and _FILES. JSON remains the raw request body until request_json() parses it. Use request_body(), request_header(), request_headers(), and cookies() for direct access.

http_status (alias status), http_header (alias header), http_content_type, and redirect control a response before headers are emitted. Header names and values reject newline injection. send_file(path) finalizes a response as a file response.

Sessions and security

Session APIs require POLONIO_SESSION_SECRET. The Reference Distribution stores JSON session data in an HMAC-SHA256-signed polonio_session cookie; invalid signatures are not loaded. csrf_token() and csrf_verify(token) are session-backed. Password and secure-token helpers are also Web Runtime APIs.

Data Runtime

The Data Runtime supplies the Reference Distribution's sandboxed storage and SQLite APIs. POLONIO_STORAGE_PATH is the reference storage root for files, directories, SQLite database paths, temporary uploads, downloads, and mail outbox files. Paths must be relative and may not escape the root.

Multipart temporary files are created beneath tmp/uploads; move a supplied _FILES object with upload_save(file, path). send_mail(to, subject, body[, headers]) writes an RFC-like .eml file beneath outbox. SMTP is not implemented.

See the Builtin Reference for signatures and the Examples page for storage, SQLite, upload, download, and mail routes.

Reference Distribution Server Limitations

The development server is single-threaded, sequential, and loopback-only. It has no TLS, keep-alive, streaming, or chunked request-body support. It accepts HTTP/1.1 GET/POST, limits request headers to 64 KiB and bodies to 8 MiB, and closes each connection. Use it for local development, not public production deployment.
